# 先定层，再定因

「卡」不是一种症状，是一组症状的统称：界面渲染慢、请求排队、链路丢包、服务端处理慢——四种表现长得几乎一样。只看本机进程，等于只在有光的地方找。

## 探针（跑完才有资格谈原因）

| 探针 | 做法 | 怎么读 |
|---|---|---|
| 分段计时 | `curl -s -o /dev/null -w 'dns=%{time_namelookup} tcp=%{time_connect} tls=%{time_appconnect} ttfb=%{time_starttransfer} total=%{time_total}\n' <url>` | TTFB 占大头 → 服务端处理；下载占大头 → 带宽/CDN；TCP/TLS 占大头 → 链路、代理、握手 |
| 浏览器对照 | F12 → Network，比 `Waiting (TTFB)` 与 `Content Download` | 同上，还能区分首字节与传输 |
| 换一条网络 | 同一操作，手机热点 vs 原链路 | 两条都慢 → 服务端；只有一条慢 → 本机/链路/DNS/代理/MTU |
| 服务端侧 | status page、换地区、第二个账号、同一时段他人反馈 | 有公告或他人同时反馈 → 基本可定 |

## 判定

- 三个探针都指向客户端，才轮到进程、内存、GPU、渲染。
- 只有一两个指向客户端、其余指向服务端 → 按服务端处理，同时保留客户端证据。
- 判不出来 → 明说「未定层」，列出还差哪个探针。不要给原因。

## 硬规则

1. **无层判定，不给原因，不改配置。** 改配置不可逆，猜出来的改动会把一个问题变成两个。
2. **两次修复没改善测量值 → 全部回退**，回到定层。第三次补丁不是方案。
3. **本机证据要能自证**：贴进程/端口的原始输出，不写「看起来是某某占用」。
4. 用户说「别人那儿也慢」时，这句话优先于任何本机指标。

## 报告模板

```text
层：<网络 / 服务端 / 客户端 / 未定>
证据：<哪个探针、什么数字>
下一步：<补哪个探针，或针对该层的具体动作>
```
